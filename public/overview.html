Section 02

User Roles & Access Model

Access is no longer tied to a fixed list of roles. The system now uses module-based, permission-driven access control (RBAC). Each role is simply a bundle of permissions, and each user is assigned one role. Every screen the user sees is decided by the modules their role can access.

2.1 — How Access Works (Module-Based RBAC)

A permission is made of two parts: a module (what part of the system, e.g. JOB_CARD) and an action (what they can do with it). Roles and permissions are fully admin-configurable — the Super Admin can create new roles, rename them, and switch any module on or off for each role from User Management.

🧩

Modules

The areas of the system — Gate Entry, QC Inspection, Job Cards, Workshop, Washbay, Billing and more. A role only sees modules it has been granted.

⚙️

Actions

What a role can do inside a module: view, create, edit, delete, and approve.

🛠️

Roles are Configurable

The Super Admin creates roles and assigns module permissions. Only the Super Admin role itself is protected — it cannot be edited or deleted.

🔐
Super Admin is absolute

The Super Admin bypasses every permission check and can access all modules. Permission changes take effect almost immediately (the system caches permissions for a few minutes). Some users can also be limited by shop scope (which workshop they belong to) or restricted to warranty-only job cards.

2.3 — Default Roles & Permissions

The system seeds ten roles out of the box. Because access is permission-driven, several roles intentionally span more than one workflow module (for example, the QC Inspector handles both QC-In and QC-Out, and the Foreman runs both Workshop and Washbay) — so there is no separate "Washbay Operator" or "Warranty Storekeeper" role. The nine active roles are shown below; the Super Admin can add more or deactivate any role at any time (a deactivated role can no longer log in). The Receptionist role has been deactivated and is therefore not listed here — see 2.4.

🧾

Self-service role. The customer reviews and approves the shared estimate online — no staff login required.

Section 03

Complete Workflow — Step by Step

This section walks through every stage of the vehicle's journey. Each stage shows who performs it, the visual flow, and what status the vehicle / job card lands in.

3.1 — Appointment Booking (Front Desk — Appointments module)

The journey usually begins with a booking. Front-desk staff search for the customer, pick the vehicle, choose a service type and an available time slot, and confirm — generating a booking reference. Walk-ins without an appointment are also supported (the journey then starts at Gate Entry). See the note in Section 2.4 — the Receptionist role that previously owned this module has been deactivated.

    Front-desk staff search by phone number, VIN or registration. Existing customers (and their vehicles) load automatically; new customers are added on the spot.

  • 2

    Choose the service type and note the customer's complaints. These complaints carry forward to Gate Entry and the Job Card.

  • 3

When the vehicle arrives, the Gate Keeper finds the pending appointment by plate; all customer, vehicle and complaint details pre-fill, and the appointment moves to CHECKED_IN.

💡
How the Admin Sets This Up

Under Model Service Types, the Admin maps each Make → Model → Series (Model Code) + service category to its standard parts list. Once mapped, the Service Advisor gets those parts auto-loaded every time.

🎯
Matching is by Model Code, not the model name Updated

Bundles are now fetched using the vehicle's stable Model Code (the Evolve MM code, e.g. 18667525), with a trimmed/case-insensitive model-name fallback. This fixes the earlier "series mismatch" where a small spelling/whitespace difference between the vehicle's model text and the assignment stopped parts from loading. The assignment screen therefore includes a third Series cascade (Make → Model → Series) so each bundle is tied to a specific Model Code.

Section 07

Admin Controls

The Super Admin configures the system so everything downstream runs automatically.

Master Data & Access Setup

  • A
    Roles & Permissions

    Create roles and switch modules on/off per role (User Management). Build the operational roles for the newer modules (Technician, Workshop, QC Out, Washbay, Warranty, Billing, Gate Release).

  • B
    User Accounts

    Create staff accounts, assign a role, and optionally set shop scope or warranty-only restrictions. Deactivate when staff leave.

  • C
    Service Types & Categories

    Maintain the Service Type and Service Category lists used on the job card.

  • D
    Model → Parts Assignments

    Map each Make → Model → Series (Model Code) + service category to its standard parts (Model Service Types). This powers parts auto-loading, which now matches vehicles by their Model Code. See Section 04.

  • E
    Slot Configuration

    Set time-slot capacity for appointment booking.

  • F
    Evolve Technician Mapping & Profile

    When creating or editing a user whose role is Technician, three technician-only fields appear in the same Add/Edit User form: Evolve Technician (links the user to their Evolve TechnicianNo so labour hours post to the correct person — required), Ability (an informational productivity factor 0.00–1.00, optional, never sent to Evolve), and Designation (job grade — Service Mechanic, Major Shop Mechanic, Repair Shop Assistant, Apprentice — optional, and not a role/permission). All three are shown only for the Technician role; switching the role away clears them. This replaces the earlier standalone Technician Mapping screen — it now lives inside User Management. Note: the client technician spreadsheet has no unique key, and names don't reliably match Evolve (duplicate surnames, spelling differences), so these values are entered manually. If spreadsheet import is ever wanted, the sheet must include the Evolve TechNo as the join key.

  • G
    Designation Master

    Technician Designations (job grades such as Service Mechanic, Major Shop Mechanic, Repair Shop Assistant, Apprentice) are managed independently from the Designations menu (admin). The page provides a full master-data CRUD:

    • List + search + status filter — a paginated table showing Name, Description, Assigned count and a Status badge, with a search box and an All / Active / Inactive filter.
    • Add / Edit — create or rename a designation (name is required and unique, case-insensitive; description optional).
    • Activate / Deactivate — no hard delete (master data). Both actions open a confirmation dialog; when deactivating a designation that is currently assigned to technicians, the dialog warns how many are affected.

    How User Management uses it: the Add/Edit User Designation dropdown (shown only for the Technician role) lists active designations only. An existing technician whose designation was later deactivated still sees it (marked inactive) in Edit mode, so it displays correctly and can be kept or changed. Deactivating a designation therefore only hides it from new selections — it never alters existing assignments.

  • H
    Labour Master New

    The standard labour descriptions used by the Job Card Labour section are managed from the Labour Master menu (admin), a master-data CRUD that mirrors the Designation Master: list + search + status filter, Add / Edit (name required, unique case-insensitive), and Activate / Deactivate with confirmation (no hard delete). The list is newest-first. The Job Card Labour Type dropdown shows active descriptions only; a Service Advisor can also type a description that isn't listed and it is saved to the master on the fly for reuse.

  • I
    Email Settings New

    Under Settings → Email, the admin configures the outbound mail transport — SMTP or Microsoft 365 (OAuth 2.0) — with sender/from details and a Test Email button. A master Enable Email toggle controls whether the system actually sends transactional emails (appointment, QC, estimate/approval). Note: Test Email always sends using the entered config, but real emails only go out when Enable Email is ON.
